# PowerSpike 0.20.1

Patch refreshes now share a five-minute active-work budget. Previously, each
request had a timeout, but a partially unavailable provider could occupy the
download worker for hours across hundreds of optional source requests.

- Each provider request uses the remaining refresh budget, capped at 45 seconds.
- Expiry stops the refresh, removes staging and preserves completed snapshots.
  It cannot be treated as an optional coverage gap and publish incomplete work.
- Publication rechecks the deadline and cancellation after waiting for the
  shared storage guard. A retry receives a fresh job and budget.

Deploy with `sudo dnf upgrade --refresh powerspike`. Existing preserved service
configuration uses the 300-second default automatically. To adjust it, set
`PS_PATCH_TIMEOUT_SECONDS` to a whole number from 1 to 1800 in
`/etc/powerspike/powerspike.env` and restart the service. Invalid settings fail
startup with a configuration error. Time in the job queue does not consume
the budget. Synchronous parsing, filesystem operations and cleanup finish
before the next deadline checkpoint.

Results remain simulations. Combat formulas, successful normalized package
bytes and scenario formats are unchanged. Older saved-model notices can appear
because the package loader participates in the model fingerprint. This release
adds software reliability checks, with no new in-game combat measurements.

Local core/source, frontend/combat, TLS outage/recovery, standalone runtime,
concurrency and extracted-RPM checks passed. The TLS fixture checks a two-second
refresh budget across successive slow optional sources, preserved cached data,
staging cleanup and successful retry after provider recovery.

Developer details and deadline limits are documented in
[patch refresh deadlines](https://github.com/tjisse/powerspike-janet/blob/v0.20.1/docs/patch-refresh-deadlines.md).
